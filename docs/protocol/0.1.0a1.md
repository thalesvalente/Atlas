# Caderno Scientific Snapshot — candidato 0.1.0a1

**Estado:** CANDIDATE / PENDING_HUMAN. A implementação e os exemplos são ensaios
reversíveis. A adoção como contrato estável e qualquer transformação de acervo
real dependem da decisão explícita sobre ADR-0002. Data da proposta: 24/10/2026.

Identificador desta versão:
<https://github.com/thalesvalente/Atlas/blob/feat/atlas021-interface-protocol/docs/protocol/0.1.0a1.md>.
A descrição resolve na branch candidata após sua publicação; o digest deste
documento acompanha a entrega. Esta branch não é um identificador permanente.
Uma versão estável deve fixar publicação persistente e compatibilidade antes de
uso operacional. Não existe aprovação presumida por publicação ou CI.

## 1. Escopo e fontes normativas

Este candidato restringe [RO-Crate 1.3](https://www.researchobject.org/ro-crate/specification/1.3/)
e [Process Run Crate 0.6](https://www.researchobject.org/workflow-run-crate/profiles/0.6/process_run_crate/)
para snapshots científicos de múltiplos produtores. Ele acrescenta apenas as
distinções necessárias a projetos/experimentos, resultados parciais, revisão,
ausência, proveniência temporal e disponibilidade. RF/RNF/RES não são tipos do
núcleo. Não exige Atlas, um produtor particular, SaaS ou banco específico.

Os verbos MUST/MUST NOT indicam obrigações deste perfil candidato. Não constituem
certificação de conformidade geral de grafos JSON-LD nem aceite de dados científicos.
O schema em `packages/protocol/src/caderno_protocol/resources/schema.json` verifica
forma; o SDK verifica relações, identidade, tipos, estados e caminhos. Uma
validação externa da base RO-Crate complementa essas verificações.

## 2. Serialização suportada

Um snapshot contém `ro-crate-metadata.json`, UTF-8, objeto com exatamente `@context`
e `@graph`. A forma JSON-LD é compactada e achatada: entidades completas estão
somente em `@graph`; relações são referências `{"@id": "..."}`. Objetos anônimos,
contextos adicionais/remotos, `@reverse`, `@list`, redefinições de prefixo e grafos
embutidos não são suportados. Propriedades extensíveis usam namespace explícito.

O contexto MUST ser exatamente:

```json
[
  "https://w3id.org/ro/crate/1.3/context",
  {
    "cp": "https://github.com/thalesvalente/Atlas/ns/caderno#",
    "prov": "http://www.w3.org/ns/prov#"
  }
]
```

O SDK usa a cópia local do contexto RO-Crate, com digest em `context-catalog.json`.
Nenhum contexto ou referência dispara acesso à rede. O namespace `cp` é um IRI
de vocabulário definido neste documento, não uma API. Sem expansão genérica,
a forma restrita e a tabela fixa de termos permitem examinar as relações
diretamente; formas semanticamente equivalentes fora desse subconjunto são
rejeitadas explicitamente, sem alegação de que sejam JSON-LD inválido em geral.

O descritor `ro-crate-metadata.json` MUST ser `CreativeWork`, ter `about` apontando
para `./` e `conformsTo` para `https://w3id.org/ro/crate/1.3`. O root `./` MUST ser
`Dataset`, com `name`, `description`, `datePublished` e `license`. `datePublished`
é a publicação deste snapshot, nunca uma data científica fabricada. `license`
descreve os direitos realmente conhecidos: os exemplos próprios declaram que
nenhuma licença foi concedida. Isso não escolhe a licença do software.

O root declara em `conformsTo` exatamente este perfil e Process Run 0.6. Cada
perfil possui entidade contextual com tipos `CreativeWork` e
`http://www.w3.org/ns/dx/prof/Profile`, `name` e `version`. A URI descritiva deve
resolver para leitura humana, conforme a seção [Profiles do padrão](https://www.researchobject.org/ro-crate/specification/1.3/profiles.html).

## 3. Entidades e relações

| Entidade | Forma mínima | Obrigatoriedade e relação |
|---|---|---|
| Snapshot | `Dataset`, ID `./` | Sempre; `hasPart` lista todos os outros Dataset/File e `mentions` lista as execuções |
| Projeto | `@type: ["Dataset", "cp:Project"]` | Zero ou mais; nome e ID absoluto com namespace do produtor |
| Experimento/investigação | `@type: ["Dataset", "cp:Experiment"]` | Cada execução aponta a um; `isPartOf` aponta a exatamente um projeto |
| Execução/atividade | `CreateAction` | `instrument`, `agent`, `cp:experiment`, estados, síntese e origem temporal explícitos |
| Software | `SoftwareApplication` | Nome, URL informativa e versão; nunca executado pelo leitor |
| Agente | `Person` ou `Organization` | Origem declarada; não é autenticação da identidade |
| Artefato/evidência | `File` | ID relativo seguro ou URI HTTP(S); disponibilidade declarada, formato e digest opcionais |
| Métrica/parâmetro | `PropertyValue` | `propertyID`, `cp:valueType`, valor ou motivo de ausência; unidade numérica explícita |
| Derivação | `prov:wasDerivedFrom` | Relação opcional a entidade declarada; sem ciclos no modelo de snapshots imutáveis |

`object` e `result` são listas de referências, assim como `cp:metrics` e
`cp:parameters`. As duas últimas listas apontam a `PropertyValue`; entrada/saída
podem apontar a arquivo ou valor. Essas relações constituem a linhagem. O leitor
não completa passos ausentes e não transforma uma ligação declarada em execução
reproduzida. Evidência é um papel do artefato associado à atividade; não implica
que o conteúdo prova a afirmação científica.

Todos os IDs de projeto, experimento e execução MUST ser URN ou URI absoluta
sob namespace do produtor. IDs iguais no mesmo grafo são erro; nunca há merge
silencioso. Referências estruturais pendentes são erro. Caminhos de payload que
se igualem após percent-decoding, normalização Unicode NFC e casefold também
são erro, para evitar ambiguidade entre plataformas.

## 4. Estados, medições e tempo

`cp:executionStatus` e `cp:reviewStatus` MUST existir separadamente. A interface
mostra os valores declarados do perfil, não conclui ciência a partir de um
processo que terminou.

| Execução exata no perfil | `actionStatus` da base | Significado da projeção |
|---|---|---|
| `COMPLETED` | `http://schema.org/CompletedActionStatus` | A execução declarou conclusão |
| `FAILED` | `http://schema.org/FailedActionStatus` | A execução declarou falha |
| `RUNNING` | `http://schema.org/ActiveActionStatus` | A execução declarou atividade |
| `PARTIAL` | `http://schema.org/FailedActionStatus` | Não houve conclusão integral; podem existir resultados parciais |
| `UNKNOWN` | `http://schema.org/PotentialActionStatus` | Projeção conservadora sem afirmar sucesso ou execução confirmada |

A última linha não declara que houve planejamento, início ou falha. É uma
limitação de expressividade do enum da base: um leitor genérico sem `cp` não
recupera a diferença entre estado desconhecido e potencial. O perfil preserva
essa diferença em `cp:executionStatus`; não a descarta. Um produtor que somente
desconhece se a execução terminou MUST usar `UNKNOWN`, e não presumir `PARTIAL`.
O status de revisão usa `UNKNOWN`, `HOLD`, `ACCEPTED`, `REJECTED` ou
`NOT_APPLICABLE`; seu significado é uma declaração do produtor, sem autoridade
outorgada pelo SDK. Registros com `cp:synthetic: true` não podem declarar ciência
`ACCEPTED` neste perfil de demonstração.

Cada valor declara `cp:valueType` entre `number`, `integer`, `string` e `boolean`.
Booleanos não são números. Valores numéricos são finitos; NaN/Infinity são
rejeitados. Números exigem `unitText`; use `1` para quantidade adimensional.
`cp:precision` opcional registra casas decimais declaradas, sem aumentar a
precisão do original. Ausência usa valor omitido/null com `cp:missingReason`
não vazio. Em RDF, null não gera um valor; o motivo explícito mantém a ausência
interpretável. Nunca substituir ausência por zero.

O leitor de referência preserva inteiros como inteiros Python. Para literais
JSON decimais, exige que `Decimal(literal) == Decimal(str(float(literal)))` e que
o resultado seja finito. Assim, `0.1` é suportado, mas
`0.123456789012345678901`, overflow e underflow que alteram o valor são recusados
com `SOURCE_INVALID`, sem arredondar a fonte. Essa restrição verifica o roundtrip
decimal da representação suportada; não afirma aritmética decimal exata em
operações binárias. A grafia original, zeros finais e bytes continuam no
documento fonte; `cp:precision` registra a precisão declarada. Consumidores que
transformam esses números para JavaScript ou outro runtime MUST preservar o
valor inteiro/decimal ou apresentar uma falha explícita, sem coerção silenciosa.

Comparações só são justificadas entre o mesmo `propertyID`, tipo numérico e
unidades compatíveis. A implementação mínima compara unidades literalmente
iguais; conversões não são implícitas. Valores com nomes iguais e unidades
distintas não recebem diferença numérica calculada.

`startTime` e `endTime`, quando conhecidos, usam ISO 8601 com timezone. Início
posterior ao fim é erro. `cp:timestampOrigin` é `DECLARED`, `OBSERVED` ou `UNKNOWN`.
O exportador não substitui tempo desconhecido pelo horário de transformação.
Campos originais e sua interpretação pertencem ao manifesto separado da
transformação, preservado sob a visibilidade da fonte.

## 5. Persistência, integridade e recuperação

O backend de referência lê diretório, arquivo de metadados ou ZIP explicitamente
selecionado. Uma publicação produz novo snapshot, não modifica o anterior.
Conflito de ID dentro de snapshot rejeita a entrada; versões diferentes de uma
fonte permanecem fontes distintas até decisão explícita de resolução. Índices
da UI são derivados e podem ser descartados/reconstruídos; eles não publicam
ciência nem substituem o snapshot como autoridade.

`cp:sha256` representa SHA-256 dos bytes exatos de um payload; `contentSize`
representa seu comprimento em bytes. O digest do metadata igualmente mede seus
bytes. Não há canonização JSON-LD, assinatura ou inferência de autoria/data.
Reformatar JSON pode preservar significado e mudar digest. O round-trip
garantido pelo SDK é de transporte dos bytes e de recuperação dos campos
definidos, não de identidade entre quaisquer grafos RDF equivalentes.

`cp:availability` declara `PRESENT`, `MISSING`, `EXTERNAL` ou `UNKNOWN`. O resultado
observado pelo leitor é separado: `AVAILABLE`, `AVAILABLE_UNVERIFIED`, `MISSING`,
`EXTERNAL_UNRESOLVED`, `UNAVAILABLE`, `INTEGRITY_MISMATCH` ou limite de leitura.
Ausência de payload não apaga o registro. `report.valid` informa a verificação
do perfil restrito e dos digests de payloads que puderam ser inspecionados;
avisos de ausência/disponibilidade têm de ser mostrados junto ao resultado.
Isso não equivale a atestar que todo payload exigido por um RO-Crate attached
está presente: a validação externa faz essa verificação separadamente.

Arquivos grandes podem ser referências HTTP(S), sem download automático.
Endereços não constituem autorização para buscar, montar, executar ou escrever.
Fontes privadas, seus paths e seus digests não devem ser exportados publicamente
sem a aprovação específica de compartilhamento.

## 6. Limites e conteúdo não confiável

| Limite | Valor no leitor de referência |
|---|---:|
| Metadata | 2 MiB |
| Entidades | 10.000 |
| Relações | 100.000 |
| Profundidade de dados | 20 |
| Payload lido por arquivo | 8 MiB |
| Payloads lidos por abertura | 32 MiB |
| ZIP comprimido | 64 MiB |
| ZIP expandido | 32 MiB |
| Membros ZIP | 4.096 |
| Razão de compressão por membro | 200, acima de 1 KiB |

ZIP é lido sem extração. Links simbólicos, arquivos especiais, caminhos
absolutos/traversal, aliases de caminho, criptografia e múltiplos documentos de
metadata são rejeitados. HTML e código anexados não são executados. A proteção
de paths reduz o risco de entradas não confiáveis; não certifica ausência de
corridas em um host adversarial nem autoriza manutenção/aposentadoria física.

## 7. Compatibilidade e evolução

Versão/contexto/perfil desconhecidos resultam em erro explícito. Não há downgrade
ou transformação silenciosa. Este candidato não importa `.eln` 1.2 como se
fosse 1.3 e não promete consumir qualquer RO-Crate existente. O exemplo oficial
incluído no repositório é lido e rejeitado com razões verificáveis.

O SDK `caderno-protocol` não importa interface ou produtor. O modelo derivado
retém `entities` originais e é reconstruível. Não existe API de aprovação,
execução experimental, migração histórica ou retirada de arquivos.
Alteração incompatível futura exige nova versão, testes e mapeamento explícito;
aplicação ao acervo permanece separada e sujeita aos gates próprios.
